npm install @phala/aci-verifier openai

Node 20.18.1+ and Bun 1.4.0+ share the same API; the `/runtime` export selects the pinned transport.

<VerifyResponseExample1 site={site} />


`connectAci()` verifies the attestation before sending model traffic and pins TLS to a key in the
attested workload keyset. Pass `aci.fetch` only to the client that uses this gateway; it records the
exact request and response wire digests. `verifyReceipt()` fetches the matching signed receipt,
verifies those digests, and verifies the cited upstream session. Audit a response before treating
its serving path as verified.

## Browser use

The browser export can verify attestation and receipt documents, but browser JavaScript cannot
observe the server certificate SPKI. Use the Node.js or Bun runtime when model traffic must be
bound to the attested TLS key.

## Release policy

The SDK does not check whether the gateway runs a production or development dstack OS image.
The deprecated `requireProductionOs` option is ignored. For OS-image assurance, verify the same
quote, event log, and VM configuration with an independent
[dstack verifier](https://github.com/Dstack-TEE/dstack/tree/next/dstack/verifier) and require
`is_valid: true`.

Without `acceptedComposeHashes`, the client verifies that the measured compose ran in a genuine
TDX workload; it does not claim that your organization reviewed that release.

| Value | Meaning |
| --- | --- |
| `sha256(app_compose)` | Bound into RTMR3; suitable for a reviewed-release allowlist |
| `source_provenance.repo_url` and `repo_commit` | Workload-declared labels, useful for inspection but not a trust anchor |

For reviewed-release enforcement, load accepted hashes from authenticated release metadata and pair
compose appraisal with the independent OS verification above.
<a href={site.paths.measurements}>Release measurements</a> lists the current values, the GitHub release that
publishes each one, and the notice you get before they change. Never copy a compose hash from the
endpoint and trust it on first use.

## What a passing audit proves

- the TDX quote binds the fresh challenge, workload keyset, and measured compose;
- the model request used hostname-validated TLS bound to an attested SPKI;
- the signed receipt binds the exact request and response bytes to that workload; and
- a required confidential upstream was verified and its cited session is valid.

It does not prove that a release was reviewed unless an independently obtained compose allowlist was
enforced.

## Inspect the artifacts by hand

The `curl` and `jq` commands inspect artifacts; they do not verify hardware quotes, receipt signatures,
or the actual TLS channel. Before sending sensitive data, use `connectAci()` above or
<a href={site.paths.proxy}>Private AI Proxy</a>, with the [release policy](#release-policy) your
application requires.
