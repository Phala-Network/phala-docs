Returns the gateway's attestation report: the hardware-backed proof of which TEE workload is serving
the API, plus the public keys it signs with. Verify this report before trusting any
<a href={site.paths.apiReceipts}>receipt</a>. For what each field proves, see
<a href={site.paths.attestation}>Attestation report</a>.

```http
GET /v1/aci/attestation?nonce={nonce}
```

## Request

<ParamField query="nonce" type="string">
  Exactly 64 lowercase hex characters (32 random bytes). The gateway binds it into the quote's
  `report_data` so you can prove the report is not a replay.
</ParamField>

## Response

`200 OK`, `application/json`. The bare attestation report.

### Top-level fields

| Field | Type | Description |
| --- | --- | --- |
| `api_version` | string | ACI version token, for example `aci/1`. |
| `workload_keyset_digest` | string | `sha256:…` digest over the published keyset. |
| `attestation` | object | The attestation evidence and keyset (below). |
| `service_capabilities` | object | `supported_e2ee_versions`, `supported_multipart_constraint_endpoints`, and the `serving` mode. |

### `attestation` object

| Field | Type | Description |
| --- | --- | --- |
| `tee_type` | string | TEE technology, for example `tdx`. |
| `report_data` | string | Value bound into the quote. Commits to your `nonce` and the keyset. |
| `source_provenance` | object | Workload-declared `repo_url`, `repo_commit`, `image_digest`, and `image_provenance` labels. |

## Verifying the report

1. Verify `attestation.evidence.quote` against Intel DCAP collateral, and confirm its report data
   binds your `nonce` and the `workload_keyset`.
2. Recompute the JCS digest of `workload_keyset` and compare it with `workload_keyset_digest`.
3. Confirm `workload_keyset_digest` matches the receipts you verify.
4. Confirm `workload_keyset.not_after` is in the future.
5. Replay the event log to RTMR3 and confirm the measured compose hash equals
   `sha256(app_compose)`.
6. For reviewed-release enforcement, require that compose hash in an independently obtained
   allowlist. Do not treat `source_provenance` as the trust anchor.

The full verification procedure is in <a href={site.paths.verify}>Verify a response</a>.

## Legacy alias

`GET /v1/attestation/report?nonce=...&signing_algo=ecdsa` is a compatibility endpoint for legacy clients. `signing_algo` selects `ecdsa` (default) or `ed25519`; the response includes the legacy `signing_address`, `signing_algo`, and `signing_public_key`, plus an `all_attestations` compatibility entry.

Its hardware quote uses a legacy signer-and-nonce binding, rather than the canonical ACI keyset-and-nonce statement. With `version=1` (default), report data is the signer identity right-padded to 32 bytes followed by a 32-byte nonce field. With `version>=2`, the first half is SHA-256 of the signer identity concatenated with the TLS SPKI fingerprint. The signer identity is the ECDSA Ethereum address or Ed25519 public key. Legacy signing keys are resolved separately from canonical receipt-signing keys.

The nonce field is constructed as follows:

- A 64-character hexadecimal nonce is decoded to its 32 raw bytes.
- Any other non-empty nonce string is hashed with SHA-256 over its UTF-8 bytes.
- If the nonce is omitted or empty, the gateway first generates 32 random bytes, encodes them as 64 hexadecimal characters, and binds the decoded bytes.

Use this legacy report only to verify the <a href={site.paths.apiReceipts + "#legacy-alias"}>legacy signature wrapper</a> under its legacy rules. Canonical ACI verifiers must fetch `/v1/aci/attestation` and follow the canonical statement above; do not apply that statement check to a legacy quote. Upstream verification for a response is recorded in the <a href={site.paths.apiReceipts}>receipt</a> and cited <a href={site.paths.apiSessions}>session</a>.
