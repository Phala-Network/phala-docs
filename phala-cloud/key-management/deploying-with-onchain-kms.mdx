---
title: Deploying with Onchain KMS
description: Deploy a Phala Cloud CVM with independently controlled on-chain application authorization, using the Dashboard or phala CLI.
---

Onchain KMS lets a DstackApp contract govern which application configurations can receive keys. Phala's attested TEE KMS verifies the CVM and issues its disk and application keys; the on-chain contracts supply the authorization policy.

This guide covers a first deployment and the checks to perform before sending production traffic. For the contract model, see [Understanding Onchain KMS](/phala-cloud/key-management/understanding-onchain-kms).

## Prerequisites

Prepare these before opening the deployment form:

- A Phala Cloud workspace with permission and capacity to create a CVM.
- A working Docker Compose file or a deployment template. Pin production container images by digest so the approved configuration identifies the intended image.
- A browser wallet that supports the selected chain, with enough ETH to cover the contract deployment. Base uses chain ID `8453`; Ethereum mainnet uses chain ID `1`.
- A decision about who will administer the DstackApp contract. A hardware-backed wallet or a multisig is a suitable production governance setup.

For workspace-compromise protection, keep the contract administration credentials separate from the Phala workspace account and its automation. The protection depends on the approved compose hashes, the KMS's allowed OS policy, and the permissions of the contract administrators.

<Warning>
  The contract owner can manage the application's compose and device allowlists. Disabling contract implementation upgrades preserves these existing administration powers. Account availability and authorization of commands inside your application require their own controls.
</Warning>

For CLI deployments, install `phala` and authenticate to the intended workspace:

```bash
npm install -g phala
phala login
```

The Dashboard uses your browser wallet for signing. Keep its private key in the wallet. The KMS service and factory contract are resolved from the platform's catalogue for the selected chain.

## Deploying via the Dashboard

Open [Phala Cloud](https://cloud.phala.com), select the intended workspace, and click **Deploy**. You can also start from a template.

The Dashboard has two deployment layouts. The redesigned form has five steps: **Workload**, **Compute & placement**, **Secrets & keys**, **Network**, and **Review & deploy**. The classic form groups fields into sections on one page. Use the instructions for the layout displayed in your workspace.

### Step 1: Configure the workload and compute

In **Workload**, enter a name and provide the Docker Compose file. Review any template configuration, registry authentication, and pre-launch script that the application needs.

In **Compute & placement**, choose the instance size, disk, placement, and dstack OS image. Use a production OS image for a production workload. The redesigned form offers On-chain KMS for CPU deployments; choosing GPU switches its key provider to Phala KMS.

### Step 2: Select On-chain KMS

Open **Secrets & keys**. In the **Key management** card, select **On-chain KMS**, then choose **Base** or **Ethereum** under **Chain**.

Review the displayed KMS identity and contract information. The KMS instance is platform-resolved. Selecting the chain chooses the authorization network used by this deployment.

Under **DstackApp contract**, choose one of these modes:

- **Deploy new** for a new application identity. The wallet transaction happens after you submit the deployment form.
- **Use existing** to reuse a DstackApp on the selected chain. Enter **Existing contract address** and click **Check**.

The **Check** action checks for contract bytecode and a response to `allowAnyDevice()`. Treat the result as an interface check. Verify the contract's registration, owner, compose authorization, and device policy separately before reusing it.

{/*SCREENSHOT 3: Secrets & keys > Key management, On-chain KMS, chain selection, and Deploy new / Use existing.*/}

### Step 3: Enter secrets and configure networking

Enter the required environment variables in **Secrets & keys**, then configure the application's connectivity in **Network**. Use the secrets inputs for secret values; literal values embedded in Docker Compose become part of the application manifest.

For ordinary secrets input, the browser encrypts environment values to the application's environment-encryption public key before the commit request. The redesigned form also supports a pre-encrypted `encrypted_env` blob through its advanced environment-policy editor.

### Step 4: Review the application manifest

In **Review & deploy**, review **app-compose.json** and use **Download** to save a copy. Check the Docker Compose content, pre-launch script, allowed environment-variable names, key-provider identity, network policy, and public visibility settings.

The authorization value is the hash of the full application manifest. Hashing the Docker Compose YAML alone produces a different reference. Changing manifest settings can change the compose hash that needs on-chain approval.

The form also displays `mr_config_id`. For a new DstackApp, the application ID becomes known after contract deployment; the per-instance identity is normally finalized on first boot. Use the running instance's attestation for the final runtime measurement.

Click **Deploy** when the configuration is ready. Provisioning returns the selected KMS metadata, device ID, and authoritative compose hash. For a new DstackApp, the flow pauses for the contract transaction before committing the CVM.

{/*SCREENSHOT 4: Review & deploy, app-compose.json, Download, measurement display, and Deploy.*/}

### Step 5: Deploy the DstackApp contract

For **Deploy new**, a drawer titled **Configure DstackApp Contract** opens. Review **Selected KMS Service**, including its URL, chain ID, and factory contract address.

Keep **Deploy New DstackApp Contract** selected. Expand **Customize RPC Endpoint** to choose a different RPC provider when needed, and use **Test RPC** to check connectivity and the chain.

Click **Deploy & Continue** and review the transaction in your wallet. Confirm the chain, sending account, factory contract, and transaction details before approving.

The factory call is `deployAndRegisterApp`. It creates and registers a DstackApp, makes the signing account its initial owner, and initializes the compose and device policy using the provisioned values. The Dashboard's new-contract flow uses a device allowlist by default.

After confirmation, the Dashboard reads the `AppDeployedViaFactory` event to obtain the DstackApp address. This address supplies the application's on-chain identity.

{/*SCREENSHOT 6: Wallet transaction confirmation, with sensitive account information redacted.*/}

### Step 6: Complete creation and verify the instance

The Dashboard submits the commit request with the DstackApp address, provisioned compose hash, and encrypted environment values. On successful creation, the redesigned form opens the CVM instance page:

```text
https://cloud.phala.com/<workspace>/apps/<app_id>/instances/<vm_uuid>
```

Watch boot progress and application logs. Contract deployment, CVM creation, and successful workload startup are separate milestones. Complete the [verification checks](#verifying-your-deployment) before accepting production traffic.

### Using the classic deployment form

In the classic form, enter the workload and resources on the same page. Under **KMS Provider**, select the Base or Ethereum provider card, then choose a compatible node and OS image. Fill in the environment and other deployment settings, and click **Deploy**.

For a new application, the same **Configure DstackApp Contract** drawer handles the factory transaction. Its final action is **Deploy & Continue**. For an existing application, select **Use Existing DstackApp Contract**, enter **App ID**, and click **Use App ID**.

### Reusing an existing DstackApp

In the redesigned form, select **Use existing** in **Secrets & keys** and enter the contract address. The creation flow uses that address directly when continuing the provision. Reusing the contract preserves its governance policy and skips the new-contract factory transaction.

Prepare the existing contract's authorization before committing the CVM:

1. Confirm the DstackApp is registered with the selected KMS factory on the selected chain.
2. Confirm `allowedComposeHashes(composeHash)` is `true` for the full manifest being deployed.
3. Confirm the selected device is allowed through `allowedDeviceIds(deviceId)` or `allowAnyDevice()`.

A new replica may need a device allowlist transaction even when its compose is already approved. See [Device Management](/phala-cloud/key-management/device-management) for node authorization, and [Multisig and Governance](/phala-cloud/key-management/multisig-governance) for approvals controlled by a Safe or another contract.

## Deploying via the CLI

Use a dedicated deployment wallet and supply its private key through your approved secret-management workflow. The CLI accepts `PRIVATE_KEY` and `ETH_RPC_URL` environment variables as well as the corresponding flags.

For a new application on Base:

```bash
phala deploy \
  --kms base \
  -c docker-compose.yml \
  --private-key "$PRIVATE_KEY" \
  --wait
```

Use `--kms ethereum` or `--kms eth` for Ethereum mainnet. Add `--rpc-url "$ETH_RPC_URL"` to select your own RPC endpoint, and `-e .env` to supply environment variables. Gas requirements depend on the chain and current transaction pricing.

For the full command options, run:

```bash
phala deploy --help
```

For later changes to an existing CVM, use [Updating with Onchain KMS](/phala-cloud/key-management/updating-with-onchain-kms). Contract-controlled ownership uses the prepare-and-commit workflow in [Multisig and Governance](/phala-cloud/key-management/multisig-governance).

## Verifying Your Deployment

### 1. Verify the contract policy

Open the app overview:

```text
https://cloud.phala.com/<workspace>/apps/<app_id>
```

Its **On-Chain KMS** section shows **DStack KMS**, **DStack App**, and **Deployer**, with block-explorer links. The device-policy summary has a **Manage** action for the device allowlist.

Open **DStack App** on the explorer and read:

- `owner()` to identify the current governance authority. The **Deployer** row records the deployment identity; ownership can later be transferred.
- `allowedComposeHashes(composeHash)` for the approved full-manifest hash.
- `allowedDeviceIds(deviceId)` for the deployment's device, or `allowAnyDevice()` for a policy admitting all devices.

Use the correct `0x`-prefixed values for contract calls. Confirm the DstackApp is registered with the intended **DStack KMS** factory as well.

{/*SCREENSHOT 7: App overview On-Chain KMS section, explorer links, device-policy status, and Manage.*/}

### 2. Verify boot and application health

Open the instance page to check live boot progress, logs, and the application's health endpoint. A successful commit creates the instance; boot and container startup continue afterward.

For CLI inspection, use:

```bash
phala cvms get <cvm-name-or-id>
phala logs <cvm-name-or-id>
```

Treat instance state and application health as separate checks. Persisted instance details can lag live runtime state.

### 3. Verify the attested workload

Follow [Verify Your Application](/phala-cloud/attestation/verify-your-application) to verify the quote and event log against your independently approved references. Check the application identity, compose hash, OS measurement, and key-provider identity.

The approved manifest should bind production container images by digest. Keep a copy of the approved manifest and governance transaction for later comparison.

## Troubleshooting

<AccordionGroup>
  <Accordion title="On-chain KMS is unavailable in the redesigned form">
    Check the compute selection. The redesigned GPU flow uses Phala KMS and disables On-chain KMS. For CPU deployments, check the selected chain's KMS catalogue and available resources.
  </Accordion>

  <Accordion title="The wallet transaction does not open">
    Install and unlock a browser wallet that exposes an Ethereum-compatible provider. Select the chain shown in the drawer and test the RPC endpoint. If the form reports a missing device ID or compose hash, resolve the provisioning error before retrying the transaction.
  </Accordion>

  <Accordion title="The contract transaction confirmed, but CVM creation failed">
    Save the transaction hash and DstackApp address. Check the contract state on the explorer and resolve the commit error. Reuse the confirmed DstackApp through the existing-contract option after checking its authorization policy; a new factory transaction creates another application identity.
  </Accordion>

  <Accordion title="An existing DstackApp passes Check, but deployment fails">
    Check the chain, KMS registration, approved compose hash, and device policy. The Check button probes the contract interface. On-chain admission and the CVM's boot-time attestation checks determine whether the requested deployment is authorized.
  </Accordion>

  <Accordion title="The CVM boots unsuccessfully after contract deployment">
    Review boot logs for attestation, OS-policy, compose-hash, and device-authorization errors. Compare the rejected values with the selected KMS and DstackApp state. Apply the intended governance approval through the authorized contract administrator before retrying.
  </Accordion>
</AccordionGroup>
