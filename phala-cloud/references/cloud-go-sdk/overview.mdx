<Note>
The Go SDK is currently in **beta**. The API surface may change between releases.
</Note>

The `phala` Go package provides a strongly-typed client for the Phala Cloud API. It handles authentication, automatic retries with exponential backoff, and structured error responses out of the box.

## Installation

Requires Go 1.25 or later.

```bash
go get github.com/Phala-Network/phala-cloud/go
```

## Quick Start

```go
package main

import (
	"context"
	"fmt"
	"log"

	phala "github.com/Phala-Network/phala-cloud/go"
)

func main() {
	client, err := phala.NewClient(
		phala.WithAPIKey("phak_your_api_key"),
	)
	if err != nil {
		log.Fatal(err)
	}

	user, err := client.GetCurrentUser(context.Background())
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("Hello, %s!\n", user.User.Username)
}
```

## Client Creation

### `NewClient(opts ...Option) (*Client, error)`

Creates a new Phala Cloud API client. The API key is resolved from options first, then falls back to the `PHALA_CLOUD_API_KEY` environment variable. Returns an error if no API key is available.

```go
// Minimal — reads API key from PHALA_CLOUD_API_KEY env var
client, err := phala.NewClient()
```

```go
// Explicit configuration
client, err := phala.NewClient(
	phala.WithAPIKey("phak_your_api_key"),
	phala.WithBaseURL("https://cloud-api.phala.com/api/v1"),
	phala.WithTimeout(60 * time.Second),
	phala.WithMaxRetries(10),
)
```

## Configuration Options

Every option is a function passed to `NewClient`. They follow Go's functional options pattern, so you can combine as many as you need.

| Option | Default | Description |
|--------|---------|-------------|
| `WithAPIKey(key)` | `PHALA_CLOUD_API_KEY` env var | API key for authentication |
| `WithBaseURL(url)` | `https://cloud-api.phala.com/api/v1` | API base URL (or `PHALA_CLOUD_API_PREFIX` env var) |
| `WithAPIVersion(v)` | `"2026-06-23"` | API version header value |
| `WithTimeout(d)` | no timeout | HTTP client timeout as `time.Duration` |
| `WithMaxRetries(n)` | `30` | Maximum retries for retryable errors (409/429/503) |
| `WithHTTPClient(hc)` | `&http.Client{}` | Custom `*http.Client` for full control |
| `WithUserAgent(ua)` | `DefaultUserAgent()` | Replace the User-Agent header |
| `WithHeader(key, val)` | — | Add a custom header to all requests |

### User-Agent

By default the client sends `User-Agent: phala-cloud-sdk-go/<version> go/<v>`, for example `phala-cloud-sdk-go/0.5.0 go/1.24.2`. `phala.DefaultUserAgent()` returns this string. `WithUserAgent` replaces it entirely, so a value you supply overrides the default. To keep the SDK token and add your own, prepend to the default:

```go
client, err := phala.NewClient(
	phala.WithAPIKey("phak_your_api_key"),
	phala.WithUserAgent("my-automation/2.0 "+phala.DefaultUserAgent()),
)
```

## Environment Variables

| Variable | Description |
|----------|-------------|
| `PHALA_CLOUD_API_KEY` | API key for authentication |

The client resolves environment variables automatically. If you pass an explicit option, it takes priority over the corresponding environment variable.

## Pointer Helpers

Many request structs use pointer fields for optional values. The SDK provides helper functions to make this ergonomic:

```go
phala.String("value")   // *string
phala.Int(4)            // *int
phala.Int64(100)        // *int64
phala.Float64(3.14)     // *float64
phala.Bool(true)        // *bool
```

These are especially useful when constructing request structs inline:

```go
&phala.PatchCVMRequest{
	PublicSysinfo: phala.Bool(true),
	VCPU:          phala.Int(4),
	Memory:        phala.Int(8192),
}
```

## CVM ID Resolution

The SDK automatically normalizes CVM identifiers before sending them to the API. You can pass any of the following formats to any method that accepts a `cvmID` string:

- **UUID** (with or without dashes) — dashes are stripped
- **40-char hex app ID** — `app_` prefix is added
- **Integer ID, hashed ID, or name** — used as-is

This means you never need to worry about converting between ID formats yourself.

## CVM Logs

Available in Go SDK v0.5.0 and later. The behavior described here is complete in v0.5.4, so use v0.5.4 or later.

`FetchCVMLogs` and `FollowCVMLogs` read serial, node, and container logs as text. `FetchCVMLogEntries` and `FollowCVMLogEntries` read container logs as entries with a channel and a message.

```go
// Last 100 lines of the serial console
text, err := client.FetchCVMLogs(ctx, "my-app",
	phala.LogSource{Type: "node", Channel: phala.CVMLogSerial},
	&phala.LogsOptions{Tail: 100},
)

// Follow the "api" container until ctx is cancelled
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

lines, errs := client.FollowCVMLogs(ctx, "my-app",
	phala.LogSource{Type: "container", Name: "api"},
	&phala.LogsOptions{Tail: 50},
)
for line := range lines {
	fmt.Print(line)
}
if err := <-errs; err != nil {
	var apiErr *phala.APIError
	if errors.As(err, &apiErr) {
		fmt.Println(apiErr.ErrorCode, apiErr.Suggestions)
	}
}

// Fetch the last 100 container records as entries
entries, err := client.FetchCVMLogEntries(ctx, "my-app",
	phala.LogSource{Type: "container", Name: "api"},
	&phala.LogsOptions{Tail: 100},
)
if err != nil {
	log.Fatal(err)
}
for _, entry := range entries {
	fmt.Printf("[%s] %s", entry.Channel, entry.Message)
}

// Follow the container as entries
records, errs := client.FollowCVMLogEntries(ctx, "my-app",
	phala.LogSource{Type: "container", Name: "api"},
	&phala.LogsOptions{Tail: 50},
)
for entry := range records {
	fmt.Printf("[%s] %s", entry.Channel, entry.Message)
}
if err := <-errs; err != nil {
	log.Fatal(err)
}
```

```go
func (c *Client) FetchCVMLogs(ctx context.Context, cvmID string, source LogSource, opts *LogsOptions) (string, error)
func (c *Client) FetchCVMLogEntries(ctx context.Context, cvmID string, source LogSource, opts *LogsOptions) ([]LogEntry, error)
func (c *Client) FollowCVMLogs(ctx context.Context, cvmID string, source LogSource, opts *LogsOptions) (<-chan string, <-chan error)
func (c *Client) FollowCVMLogEntries(ctx context.Context, cvmID string, source LogSource, opts *LogsOptions) (<-chan LogEntry, <-chan error)
```

`opts` may be `nil`.

| Method | Result |
|--------|--------|
| `FetchCVMLogs` | A `string`. For a container source, the SDK joins the entries into text. |
| `FetchCVMLogEntries` | `[]LogEntry`. Container sources only; a node source returns an error. |
| `FollowCVMLogs` | A channel of log text and a channel of errors. Cancel with the `ctx` you pass in. |
| `FollowCVMLogEntries` | A channel of `LogEntry` and a channel of errors. Container sources only; a node source sends an error. Cancel with the `ctx` you pass in. |

`FollowCVMLogs` and `FollowCVMLogEntries` close both channels when the follow ends. A cancelled context ends the follow without sending an error. Cancelling `ctx` also interrupts waits between reconnects. `FetchCVMLogs` and `FetchCVMLogEntries` stop when `ctx` is cancelled, including during their lookups. Any other failure is sent once on the error channel. Read the log channel until it closes, then read the error channel.

**`LogSource`:**

| Field | Type | Description |
|-------|------|-------------|
| `Type` | `string` | `"node"` or `"container"`. Set it explicitly: any value other than `"container"` is treated as a node source. |
| `Channel` | `CVMLogChannel` | Node channel: `CVMLogSerial`, `CVMLogStdout`, or `CVMLogStderr` |
| `Name` | `string` | Container name or unique container ID prefix. If empty, the SDK uses the first container in the CVM composition. See [Container names](#container-names). |

**`LogsOptions`:**

| Field | Type | Description |
|-------|------|-------------|
| `Tail` | `any` | Number of most recent lines as an `int`, or the string `"all"`. When `nil`, the server default applies. |
| `Since` | `any` | Start time as Unix seconds (`int`, `int64`, or a numeric string), an RFC 3339 string, or a relative duration such as `"10m"` (`s`, `m`, `h`, `d`). Container logs only. A node source with `Since` returns an error. |
| `Until` | `any` | End time. Same formats as `Since`. Container logs only. A node source with `Until` returns an error. |
| `Timestamps` | `bool` | Keep the timestamp prefix on container lines. Container logs only. A node source with `Timestamps` returns an error. |
| `ANSI` | `bool` | Keep ANSI escape sequences in the output. The default removes them from every line and entry, including NDJSON messages. This is an output option, so it never causes an error. |
| `Format` | `string` | `"text"` or `"ndjson"`. `FetchCVMLogEntries` reads it (default `"ndjson"`; other values return an error). A node source with `"ndjson"` returns an error. `FetchCVMLogs` and `FollowCVMLogs` return text. For containers, they read NDJSON and join the messages unless `Format` is `"text"`, which uses the plain-text transport. `FollowCVMLogEntries` also reads `Format`: other values than `"ndjson"` return an error. |

`LogEntry` has two fields: `Channel` (`"stdout"`, `"stderr"`, `"console"`, or `"stdin"`) and `Message`. `console` appears for containers started with a TTY. `Message` is exactly what the container wrote, usually ending in a newline. An empty message stays an empty string.

**Container names:**

The SDK resolves the container name once at the start of a follow, with one composition call. It tries these steps in order:

1. An exact match on a container name.
2. A unique match on the start of a container ID.
3. If `Name` is empty, the first container in the composition.

If the prefix matches more than one container, the call returns an `*APIError` with `ErrorCode` `ERR-17-001` and the message `Ambiguous container prefix '<name>': web, worker`, which lists the candidates. If nothing matches, it returns `ERR-17-007`. If the composition has no containers and returns an `error` string, for example because the CVM is stopped, the call returns an `*APIError` with that message.

A name must be 1 to 128 characters, start with a letter or digit, and then use only letters, digits, `_`, `.`, and `-`. It must not contain `..`. Other names, such as `/app`, are rejected with `ERR-17-001` before any request is sent.

**Behavior:**

- Every connection uses a fresh signed URL, with one CVM info lookup per connection.
- Follow reconnects after a stream ends or fails. Failures back off from 250 ms, doubling up to 5 s, and follow gives up after 5 consecutive failures. Starts of two connections are at least 1 s apart.
- HTTP errors are handled by status. `5xx` and `429` are failures. `401` with `ERR-17-003` fetches a new URL and retries, up to 3 times in a row. The count resets after a connection that delivered records or ended cleanly. `401` with `ERR-17-002` fetches a new URL and counts as a failure. Any other `4xx` stops follow.
- A gateway error line inside a `200` stream, or a network error, counts as a failure. A connection that delivered at least one record resets the failure count before its own failure is counted.
- Container follow always requests timestamps internally, in both the NDJSON and the text transport. It sends the caller's `Tail` until the first connection is accepted. Every later request sends `tail=all` plus `since`, and skips lines it already delivered at the boundary second, so a reconnect does not repeat output. Before any timestamped record arrives, it uses your `Since` if you set one, otherwise the second the first connection was accepted. Timestamps are removed from the output unless you set `Timestamps`.
- Container follow: if a stream ends cleanly with no new output within 10 s, it backs off and counts the end. After 5 such ends in a row, follow stops with `log stream keeps ending without new output; the container may have stopped`. A clean end after records, or after an idle connection of 10 s or more, reconnects at once and resets the count.
- Node follow never stops on a clean end. After the first connection it requests `tail=0`.
- If you set `Until`, follow finishes normally, without an error, when the stream reaches that time.
- A missing container is not retried.
- Node follow and fetch drop `[vmm heartbeat]` and `[teepod heartbeat]` lines.
- A text-format record that looks like `{"error": ...}` is treated as a guest error only at the very start of the body. Use NDJSON (the default for entries) for reliable detection.
- The helpers request CVM info with API version `2026-01-21` internally, so they work with clients configured for older versions.

For the HTTP details behind these methods, see [Fetch Logs over HTTP](/phala-cloud/monitoring/log-api).

**Errors:**

Log gateway errors are returned as `*APIError`. Check `ErrorCode` for a log error code such as `ERR-17-005`, and use `errors.As` to reach it. `Message` holds the human-readable text only, without the code. `Suggestions`, `Details`, `Links`, and `RequestID` come from the API error envelope. `StatusCode` is the HTTP status and is set only for errors returned as an HTTP response. It is `0` for client-side errors (bad container name, bad time, unsupported option) and for errors read from the body of a stream, such as a guest agent error or the stalled-stream error. Those print as their message alone, without `phala api error (status N)`.

Container logs require [Public Logs](/phala-cloud/monitoring/public-logs) to be enabled on the CVM. When it is off, container fetch and follow return an `*APIError` with `ErrorCode` `ERR-17-006` ("Container logs are disabled") before sending any log request. Follow checks this before its first log request and again on every reconnect, because each connection looks up the CVM info. Node channels are not affected.

If the agent inside the CVM cannot read a container's logs, for example because the container uses a Docker logging driver that does not support reading, the method returns an `*APIError` with `ErrorCode` `ERR-17-009` and the agent's message. This applies to text and NDJSON, in fetch and in follow. Follow stops on it. A server-returned HTTP `502` with `ERR-17-009` is different: follow reconnects.

See [Fetch Logs over HTTP](/phala-cloud/monitoring/log-api#errors) for the full error code list.
