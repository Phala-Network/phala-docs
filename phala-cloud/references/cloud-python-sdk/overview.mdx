<Note>
The Python SDK is currently in **beta**. The API surface may change between releases.
</Note>

The `phala-cloud` SDK gives you a Pythonic interface to the Phala Cloud API. It ships with both sync and async clients, Pydantic-validated responses, and a `safe_*` method pattern that lets you handle errors without try/except blocks.

## Installation

```bash
pip install phala-cloud
```

```bash
uv add phala-cloud
```

```bash
poetry add phala-cloud
```

<Note>
Requires Python 3.10 or later. The SDK depends on `httpx`, `pydantic`, and `dstack-sdk`.
</Note>

## Quick Start

<CodeGroup>

```python Sync
from phala_cloud import create_client

client = create_client(api_key="phak_your_api_key")
me = client.get_current_user()
print(me.model_dump())
```

```python Async
import asyncio
from phala_cloud import create_async_client


async def main():
    client = create_async_client(api_key="phak_your_api_key")
    me = await client.get_current_user()
    print(me.model_dump())
    await client.aclose()


asyncio.run(main())
```

</CodeGroup>

## Client Creation

### `create_client(**kwargs)` / `create_async_client(**kwargs)`

Factory functions that return a `PhalaCloud` (sync) or `AsyncPhalaCloud` (async) instance. Both accept the same configuration options.

```python
from phala_cloud import create_client, create_async_client

# Minimal — reads API key from PHALA_CLOUD_API_KEY env var
client = create_client()

# Explicit configuration
client = create_client(
    api_key="phak_your_api_key",
    base_url="https://cloud-api.phala.com/api/v1",
    version="2026-06-23",
    timeout=30.0,
)
```

### Configuration Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `api_key` | `str` | `PHALA_CLOUD_API_KEY` env var | API key for authentication |
| `bearer_token` | `str` | `PHALA_OIDC_TOKEN` env var | Bearer token; API key takes precedence |
| `workspace` | `str` | `PHALA_CLOUD_WORKSPACE` env var | Workspace slug |
| `base_url` | `str` | `https://cloud-api.phala.com/api/v1` | API base URL (or `PHALA_CLOUD_API_PREFIX` env var) |
| `version` | `ApiVersion` | `"2026-06-23"` | API version to use |
| `timeout` | `float` | `60.0` | Request timeout in seconds |
| `use_cookie_auth` | `bool` | `False` | Use cookie-based auth instead of API key |
| `headers` | `dict[str, str]` | `None` | Additional request headers |
| `http_client` | `httpx.Client` / `httpx.AsyncClient` | `None` | Bring your own httpx client |

### User-Agent

By default the SDK sends `User-Agent: phala-cloud-sdk-python/<version> python/<v> httpx/<v>`, for example `phala-cloud-sdk-python/0.4.0 python/3.13.1 httpx/0.28.1`. To use your own value, pass a `User-Agent` entry in `headers`. A header you supply overrides the default.

```python
client = create_client(
    api_key="phak_your_api_key",
    headers={"User-Agent": "my-automation/2.0"},
)
```

### API Versions

The SDK supports four API versions. The version affects response shapes for endpoints such as `get_current_user()` and `get_cvm_list()`.

```python
from phala_cloud import SUPPORTED_API_VERSIONS, DEFAULT_API_VERSION

print(SUPPORTED_API_VERSIONS)
# ("2025-10-28", "2026-01-21", "2026-05-22", "2026-06-23")
print(DEFAULT_API_VERSION)  # "2026-06-23"
```

You can switch versions on an existing client without creating a new one from scratch:

```python
legacy_client = client.with_version("2025-10-28")
```

## Sync vs. Async

Almost every method on the sync `PhalaCloud` client has an identical counterpart on `AsyncPhalaCloud`. The async version simply requires `await`. The one difference is `follow_cvm_logs`: on the async client you do not await it, you iterate the result with `async for` (see [CVM Logs](#cvm-logs)).

<CodeGroup>

```python Sync
client = create_client(api_key="phak_your_api_key")
cvms = client.get_cvm_list()
client.close()
```

```python Async
client = create_async_client(api_key="phak_your_api_key")
cvms = await client.get_cvm_list()
await client.aclose()
```

</CodeGroup>

Both clients support context managers for automatic cleanup:

<CodeGroup>

```python Sync
with create_client(api_key="phak_your_api_key") as client:
    cvms = client.get_cvm_list()
```

```python Async
async with create_async_client(api_key="phak_your_api_key") as client:
    cvms = await client.get_cvm_list()
```

</CodeGroup>

## Safe Methods

Most action methods have a `safe_*` variant that returns a `SafeResult` instead of raising exceptions. `watch_cvm_state` does not have a safe variant. This is useful when you want to handle errors as values rather than control flow.

```python
result = client.safe_get_cvm_info({"id": "my-app"})

if result.ok:
    print(result.data)
else:
    print(result.error)
```

Read more in [Error Handling](/phala-cloud/references/cloud-python-sdk/error-handling).

## CVM Logs

Available in `phala-cloud` 0.4.0 and later. The behavior described here is complete in 0.4.4, so use 0.4.4 or later.

`fetch_cvm_logs` and `follow_cvm_logs` read serial, node, and container logs. Both `PhalaCloud` and `AsyncPhalaCloud` have them. On `AsyncPhalaCloud`, `fetch_cvm_logs` is a coroutine and `follow_cvm_logs` returns an async iterator.

```python
from phala_cloud import LogAccessError, create_client

client = create_client(api_key="phak_your_api_key")

# Last 100 lines of the serial console
serial = client.fetch_cvm_logs(
    "my-app",
    {"type": "node", "channel": "serial"},
    tail=100,
)
print(serial)

# Follow the "api" container; the with block closes the stream when it exits
try:
    with client.follow_cvm_logs(
        "my-app",
        {"type": "container", "name": "api"},
        tail=50,
    ) as follow:
        for entry in follow:
            print(entry["message"], end="")
except LogAccessError as error:
    print(error.code, error.suggestions)
```

The async client has the same methods:

```python
import asyncio

from phala_cloud import LogAccessError, create_async_client


async def main() -> None:
    async with create_async_client(api_key="phak_your_api_key") as client:
        # Container entries as a list
        entries = await client.fetch_cvm_logs(
            "my-app",
            {"type": "container", "name": "api"},
            tail=100,
            format="ndjson",
        )
        for entry in entries:
            print(entry["channel"], entry["message"], end="")

        # Follow as entries; aclose() runs when the loop exits
        follow = client.follow_cvm_logs(
            "my-app",
            {"type": "container", "name": "api"},
            tail=50,
        )
        try:
            async for entry in follow:
                print(entry["message"], end="")
        except LogAccessError as error:
            print(error.code, error.suggestions)
        finally:
            await follow.aclose()


asyncio.run(main())
```

```python
def fetch_cvm_logs(
    self,
    cvm_id: str,
    source: CvmLogSource,
    *,
    tail: int | str | None = None,
    since: str | int | None = None,
    until: str | int | None = None,
    timestamps: bool = False,
    ansi: bool = False,
    format: CvmLogFormat | None = None,
    log_http: httpx.Client | None = None,
) -> str | list[CvmLogEntry]: ...

def follow_cvm_logs(
    self,
    cvm_id: str,
    source: CvmLogSource,
    *,
    tail: int | str | None = None,
    since: str | int | None = None,
    until: str | int | None = None,
    timestamps: bool = False,
    ansi: bool = False,
    format: CvmLogFormat | None = None,
    log_http: httpx.Client | None = None,
) -> LogFollowIterator[str | CvmLogEntry]: ...
```

`AsyncPhalaCloud` has the same parameters. Its `log_http` is an `httpx.AsyncClient`, `fetch_cvm_logs` is declared `async def`, and `follow_cvm_logs` returns `AsyncGenerator[str | CvmLogEntry, None]`. `LogFollowIterator` and the entry types are importable from `phala_cloud.logs`.

**Parameters:**

| Name | Type | Default | Description |
|------|------|---------|-------------|
| `cvm_id` | `str` | None | CVM identifier (name, UUID, or App ID) |
| `source` | `CvmLogSource` | None | Which logs to read (see below) |
| `tail` | `int \| str \| None` | `None` | Number of most recent lines, or `"all"`. When `None`, the server default applies. |
| `since` | `str \| int \| None` | `None` | Start time: RFC 3339 timestamp, Unix seconds, or relative duration such as `"10m"` (`s`, `m`, `h`, `d`). |
| `until` | `str \| int \| None` | `None` | End time. Same formats as `since`. |
| `timestamps` | `bool` | `False` | Prefix each container line with its timestamp. |
| `ansi` | `bool` | `False` | Keep ANSI escape sequences in the output. The default removes them from every line and entry, including NDJSON messages. This is an output option, so it never causes an error. |
| `format` | `"text" \| "ndjson"` | `None` | For a container, `fetch_cvm_logs` returns a `str` (the messages joined) unless you pass `"ndjson"`, which returns a list of entries. `follow_cvm_logs` yields entries unless you pass `"text"`, which yields text lines. Without a format, containers are read as NDJSON; `"text"` uses the plain-text transport. `"ndjson"` with a node source raises `LogAccessError`. |
| `log_http` | `httpx.Client \| None` | `None` | Your own `httpx.Client` for the log requests. When omitted, the SDK creates one and closes it when the call finishes. |

**`CvmLogSource`** is a dictionary:

| Shape | Description |
|-------|-------------|
| `{"type": "node", "channel": "serial" \| "stdout" \| "stderr"}` | A CVM-level channel |
| `{"type": "container", "name": str, "matchContainerIdPrefix": bool}` | A container. Both `name` and `matchContainerIdPrefix` are optional. `name` is a container name or ID prefix; if you omit it, the SDK uses the first container in the CVM composition. `matchContainerIdPrefix` defaults to `True`. See [Container names](#container-names). |

`since`, `until`, and `timestamps` apply to container logs only. Passing them with a node source raises `LogAccessError` with code `ERR-17-001` before any request is sent. An invalid time value does the same.

**Return types:**

| Call | Source | Result |
|------|--------|--------|
| `fetch_cvm_logs` | Node | `str` |
| `fetch_cvm_logs` | Container | `str`, or `list[CvmLogEntry]` when `format="ndjson"` |
| `follow_cvm_logs` | Node | Iterator of `str` lines, each delivered with its original newline (or lack of one), after heartbeat lines are dropped and ANSI escapes are stripped (unless `ansi` is `True`) |
| `follow_cvm_logs` | Container | Iterator of `CvmLogEntry`, or `str` lines when `format="text"` |

`CvmLogEntry` is a dictionary: `{"channel": "stdout" | "stderr" | "console" | "stdin", "message": str}`. `console` appears for containers started with a TTY. `message` is exactly what the container wrote, usually ending in a newline. An empty message stays an empty string. The types are importable from `phala_cloud.logs`.

### Container names

The SDK resolves the container name once at the start of a follow, with one composition call. It tries these steps in order:

1. An exact match on a container name.
2. A unique match on the start of a container ID, unless `matchContainerIdPrefix` is `False`.
3. If you gave no name, the first container in the composition.

If the prefix matches more than one container, the SDK raises `LogAccessError` with code `ERR-17-001` and the message `Ambiguous container prefix '<name>': web, worker`, which lists the candidates. If nothing matches, it raises `LogAccessError` with code `ERR-17-007`. If the composition has no containers and returns an `error` string, for example because the CVM is stopped, the SDK raises `LogAccessError` with that message.

A name you pass must be 1 to 128 characters, start with a letter or digit, and then use only letters, digits, `_`, `.`, and `-`. It must not contain `..`. Other names, such as `/app`, are rejected with `ERR-17-001` before any request is sent.

### Cancellation

- Sync follow: leaving the loop with `break` does not close the HTTP response. Call `close()` on the returned iterator, or use it in a `with` block, which calls `close()` for you. `close()` also works from another thread and interrupts a wait between reconnects.
- Async follow: leave the loop and call `await follow.aclose()`, or cancel the task that is iterating. Waits between reconnects are interrupted.
- Async `fetch_cvm_logs`: cancel the task that is awaiting it.
- Sync `fetch_cvm_logs` is a single blocking call. It cannot be cancelled while a request is in progress.


**Behavior:**

- Every connection uses a fresh signed URL, with one CVM info lookup per connection.
- Follow reconnects after a stream ends or fails. Failures back off from 250 ms, doubling up to 5 s, and follow gives up after 5 consecutive failures. Starts of two connections are at least 1 s apart.
- HTTP errors are handled by status. `5xx` and `429` are failures. `401` with `ERR-17-003` fetches a new URL and retries, up to 3 times in a row. The count resets after a connection that delivered records or ended cleanly. `401` with `ERR-17-002` fetches a new URL and counts as a failure. Any other `4xx` stops follow.
- A gateway error line inside a `200` stream, or a network error, counts as a failure. A connection that delivered at least one record resets the failure count before its own failure is counted.
- Container follow always requests timestamps internally. It sends the caller's `tail` until the first connection is accepted. Every later request sends `tail=all` plus `since`, and skips lines it already delivered at the boundary second, so a reconnect does not repeat output. Before any timestamped record arrives, it uses your `since` if you set one, otherwise the second the first connection was accepted. Timestamps are removed from the output unless you set `timestamps=True`.
- Container follow: if a stream ends cleanly with no new output within 10 s, it backs off and counts the end. After 5 such ends in a row, follow raises `LogAccessError` with the message `log stream keeps ending without new output; the container may have stopped`. A clean end after records, or after an idle connection of 10 s or more, reconnects at once and resets the count.
- Node follow never stops on a clean end. After the first connection it requests `tail=0`.
- If you set `until`, follow finishes normally, without an error, when the stream reaches that time.
- A missing container is not retried.
- Node follow and fetch drop `[vmm heartbeat]` and `[teepod heartbeat]` lines.
- A text-format record that looks like `{"error": ...}` is treated as a guest error only at the very start of the body. Use NDJSON (the default for entries) for reliable detection.
- The helpers request CVM info with API version `2026-01-21` internally, so they work with clients configured for older versions.

For the HTTP details behind these methods, see [Fetch Logs over HTTP](/phala-cloud/monitoring/log-api).

**Errors:**

Log gateway errors are raised as `LogAccessError`, a subclass of `ResourceError`. Match on `code` rather than the message.

| Attribute | Type | Description |
|-----------|------|-------------|
| `code` | `str \| None` | Log error code such as `ERR-17-005`. The code is not repeated in the message, which holds the human-readable text only. |
| `http_status` | `int \| None` | HTTP status, set only for errors returned as an HTTP response. `None` for client-side errors (bad container name, bad time, unsupported option) and for errors read from the body of a stream. |
| `suggestions` | `list[str] \| None` | Suggested fixes from the API |

`LogAccessError` is a `ResourceError`, so it also carries `error_code`, `structured_details`, `links`, and `request_id` from the API error envelope.

Container logs require [Public Logs](/phala-cloud/monitoring/public-logs) to be enabled on the CVM. When it is off, container fetch and follow raise `LogAccessError` with code `ERR-17-006` ("Container logs are disabled") before sending any log request. Follow checks this before its first log request and again on every reconnect, because each connection looks up the CVM info. Node channels are not affected. A missing container raises `LogAccessError` with code `ERR-17-007` (see [Container names](#container-names)).

If the agent inside the CVM cannot read a container's logs, for example because the container uses a Docker logging driver that does not support reading, the method raises `LogAccessError` with code `ERR-17-009` and the agent's message. This applies to text and NDJSON, in fetch and in follow. Follow stops on it. A server-returned HTTP `502` with `ERR-17-009` is different: follow reconnects. See [Fetch Logs over HTTP](/phala-cloud/monitoring/log-api#errors) for the full error code list.

## Utility Functions

The SDK also exports standalone utility functions for working with CVM configurations:

```python
from phala_cloud import (
    async_encrypt_env_vars,
    encrypt_env_vars,
    get_compose_hash,
    get_mr_config_id_hex,
    parse_env,
    parse_env_vars,
    verify_env_encrypt_public_key,
)
```

| Function | Description |
|----------|-------------|
| `encrypt_env_vars(envs, public_key_hex)` | Encrypt environment variables synchronously |
| `async_encrypt_env_vars(envs, public_key_hex)` | Encrypt environment variables asynchronously |
| `get_compose_hash(...)` | Compute the hash of canonicalized `app-compose.json` |
| `get_mr_config_id(...)` | Compute V2 `mr_config_id` from byte inputs |
| `get_mr_config_id_hex(...)` | Compute V2 `mr_config_id` from hex inputs |

| `verify_mr_config_id(...)` | Verify a V2 `mr_config_id` |

| `parse_env(path)` | Parse a `.env` file into key-value pairs |
| `parse_env_vars(content)` | Parse dotenv content string into key-value pairs |
| `verify_webhook_signature(...)` | Verify HMAC-SHA256 webhook signature with timestamp tolerance |
| `parse_webhook_event(...)` | Verify signature and parse webhook event in one step |

### Encrypt environment variables

Pass the output of `parse_env_vars` or a sequence of `dstack_sdk.EnvVar` objects to either helper. The public key must be a hex string.

```python
from phala_cloud import encrypt_env_vars, parse_env_vars

envs = parse_env_vars("API_TOKEN=secret")
encrypted = encrypt_env_vars(envs, public_key_hex)
```

In async code, use `await async_encrypt_env_vars(envs, public_key_hex)`. Both helpers return the encrypted string.

<Warning>
`encrypt_env_vars` now returns a string synchronously. If you previously awaited it, replace `await encrypt_env_vars(...)` with `await async_encrypt_env_vars(...)`.
</Warning>
