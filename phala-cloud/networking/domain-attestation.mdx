This guide shows how to verify that TLS certificates are controlled by a TEE using cryptographic attestation.

For application code verification, see your app's attestation documentation. For security concepts, see [Security Architecture](/phala-cloud/networking/security).

## Which Verification Guide to Follow?

The verification method depends on what the application deployer chose:

| Domain Type | When to Use | Operator |
|-------------|-------------|----------|
| **Gateway Domains** (`*.phala.network`) | Your app uses Phala's gateway domain | Phala Cloud |
| **Custom Domain** | Your app uses a custom domain with dstack-ingress | Developer |

Both provide cryptographic proof of TEE control over TLS certificates. The difference is who operates the certificate infrastructure.

## Gateway Domains

Gateway domains expose attestation endpoints that prove TEE control over TLS certificate private keys.

### What You'll Verify

The gateway TEE publishes cryptographic evidence at `https://GATEWAY-DOMAIN/.dstack/` endpoints that proves:

1. The TLS certificate private keys are generated and controlled by the gateway TEE
2. TEE hardware backs all certificate operations
3. Only the TEE-controlled Let's Encrypt account can issue certificates for gateway domains
4. All historical certificates are accounted for via TEE remote attestation

### 3-Step Verification

**Example**: We'll use `gateway.dstack-pha-prod7.phala.network` - replace with your gateway domain.

#### Step 1: Get Gateway Evidence

The gateway publishes evidence through three endpoints:

```bash
# Get ACME certificate information
curl -s "https://gateway.dstack-pha-prod7.phala.network/.dstack/acme-info" | jq > acme-info.json

# Get gateway application information
curl -s "https://gateway.dstack-pha-prod7.phala.network/.dstack/app-info" | jq > app-info.json
```

**Expected output from acme-info.json**:
```json
{
  "account_uri": "https://acme-v02.api.letsencrypt.org/acme/acct/2584877296",
  "account_quote": { tdx-quote-with-eventlogs },
  "hist_keys": ["<base64-pubkey-1>"],
  "quoted_hist_keys": [
    {"public_key": "<base64>", "quote": { tdx-quote-with-eventlogs } },
    {"public_key": "<base64>", "quote": { tdx-quote-with-eventlogs } }
  ],
  "active_cert": "-----BEGIN CERTIFICATE-----\n...",
  "base_domain": "dstack-pha-prod7.phala.network"
}
```

**What this means**: The gateway provides its Let's Encrypt account, all certificate public keys (current and historical), and TDX quotes proving the TEE generated these keys.

#### Step 2: Verify Certificate Matches TDX Quotes

Check that the served certificate matches the TEE-quoted keys:

```bash
# Get the public key from the served certificate
openssl s_client -connect gateway.dstack-pha-prod7.phala.network:443 </dev/null 2>/dev/null | \
  openssl x509 -pubkey -noout > served-pubkey.pem

# Get the public key from the evidence certificate
cat acme-info.json | jq -r '.active_cert' | \
  openssl x509 -pubkey -noout > evidence-pubkey.pem

# Compare the public keys
diff served-pubkey.pem evidence-pubkey.pem
```

**Expected**: No output (files are identical).

Cryptographically validate every quote before interpreting its `report_data`:

1. Submit each `account_quote` and `quoted_hist_keys[].quote` value to a trusted
   DCAP verifier.
2. Validate Intel collateral, TCB status, debug policy, and the expected gateway
   application measurements.
3. Compare the verifier-authenticated `report_data` with the account or public-key
   binding defined by the audited gateway implementation.
4. Match `active_cert` and the served certificate as shown above.

A hash found in raw quote text is only a byte-presence check. Follow the
[Attestation Verification tutorial](/phala-cloud/attestation/verification-guide)
for cryptographic quote validation.

#### Step 3: Check Domain Protection and Certificate History

Review the gateway's issuance policy and certificate history:

```bash
# Check ALL certificates ever issued for the gateway domain
curl -s "https://crt.sh/?q=%.dstack-pha-prod7.phala.network&output=json" | \
  jq -r '.[] | "\(.not_before) to \(.not_after): \(.issuer_name)"' | head -10

# Get the TEE's ACME account
cat acme-info.json | jq -r '.account_uri'
# Output: https://acme-v02.api.letsencrypt.org/acme/acct/2584877296

# Check DNS CAA records for the base domain
dig +short CAA dstack-pha-prod7.phala.network
```

**Example output**:
```
# Certificate history
2025-01-15T08:23:45 to 2025-04-15T08:23:44: C=US, O=Let's Encrypt, CN=E5
2024-12-01T10:15:22 to 2025-03-01T10:15:21: C=US, O=Let's Encrypt, CN=R3

# ACME account
https://acme-v02.api.letsencrypt.org/acme/acct/2584877296

# CAA record
0 issue "letsencrypt.org;validationmethods=dns-01;accounturi=https://acme-v02.api.letsencrypt.org/acme/acct/2584877296"
```

Verify the following:

- All certificates are from Let's Encrypt (no other CAs)
- All the CAA record matches the account_uri from the TEE
- Historical keys in `hist_keys` correspond to certificates in CT logs

### Gateway Evidence Endpoints Reference

| Endpoint | Contains | Proves |
|----------|----------|--------|
| `/.dstack/index` | List of available endpoints | Gateway discovery |
| `/.dstack/app-info` | App ID, instance ID, device ID, TCB info | TEE application identity |
| `/.dstack/acme-info` | ACME account, certificate keys, TDX quotes | Certificate control and history |

The `acme-info` response structure:

| Field | Type | Purpose |
|-------|------|---------|
| `account_uri` | String | Let's Encrypt account URI |
| `account_quote` | String | TDX quote proving TEE controls the ACME account |
| `hist_keys` | Array | All certificate public keys (current + historical) |
| `quoted_hist_keys` | Array | Public keys with TDX quotes proving TEE generated them |
| `active_cert` | String | Currently active certificate (PEM format) |
| `base_domain` | String | Base domain for gateway (e.g., dstack-pha-prod7.phala.network) |

### Troubleshooting

**"Connection refused to /.dstack/ endpoints"**: These endpoints are only accessible via the gateway subdomain: `gateway.dstack-pha-prod7.phala.network`

**"Certificate doesn't match quoted keys"**: The gateway may have recently renewed certificates. Re-fetch the evidence with a fresh `acme-info` request.

**"Multiple ACME accounts in history"**: Gateway upgrades or migrations may result in new ACME accounts. Check that the CAA record matches the current account_uri, and verify old certificates have expired.

### What You've Verified

When all checks pass, you've cryptographically proven:
- **Zero-trust TLS**: The gateway TEE controls certificate private keys, verifiable via TDX attestation
- **Phala-operated infrastructure**: Phala Network operates the gateway TEE and maintains CAA records
- **Certificate transparency**: All certificates are publicly auditable via CT logs

**Key difference from custom domains**: With gateway domains, Phala operates the certificate infrastructure. With custom domains, the application deployer operates it. Both provide cryptographic proof of TEE control.

## Custom Domains

Custom domains use dstack-ingress running in your application's TEE to manage certificates. The application deployer operates the certificate infrastructure.

### What You'll Verify

The ingress publishes a manifest, certificate, ACME account metadata, and a TDX
quote at `https://your-domain.com/evidences/`. Verification establishes four
separate facts:

1. Intel's trust chain authenticates the TDX quote and its TCB status
2. The verified quote's `report_data` binds the evidence manifest to that TEE
3. The evidence certificate matches the certificate served to clients
4. DNS CAA and Certificate Transparency records match your issuance policy

Evidence binding alone does not prove private-key exclusivity. Complete the
application measurement review to establish which code could access the key.

### Prerequisites

You need your domain name plus `curl`, `jq`, `openssl`, `sha256sum`, and `dig`.
You also need a trusted DCAP verifier that returns the authenticated
`report_data` field. See [Attestation Verification](/phala-cloud/attestation/verification-guide).

### Verification

#### Step 1: Authenticate the evidence manifest

```bash
DOMAIN=your-domain.com
CERT_FILE="cert-${DOMAIN}.pem"
BASE_URL="https://${DOMAIN}/evidences"

curl --fail --http1.1 -sS -O "${BASE_URL}/quote.json"
curl --fail --http1.1 -sS -O "${BASE_URL}/sha256sum.txt"
```

1. Extract the quote hex from `quote.json`.
2. Cryptographically validate the quote signature, Intel collateral, TCB status,
   and debug policy with a trusted DCAP verifier.
3. Read `report_data` from the verifier's authenticated result.
4. Compute `sha256sum sha256sum.txt`.
5. Compare that 32-byte digest with the first 32 bytes of `report_data`; the
   remaining 32 bytes must be zero.

Searching the raw quote text for a hash is only a byte-presence check. The
manifest becomes trustworthy after cryptographic quote and TCB validation.

#### Step 2: Download and check every manifest file

Release 2.6 names each certificate `cert-<domain>.pem`. Multi-domain deployments
publish one certificate file per configured domain. Download every certificate
named by the authenticated manifest before running the checksum check:

```bash
curl --fail --http1.1 -sS -O "${BASE_URL}/acme-account.json"

awk '$2 ~ /^cert-/ {print $2}' sha256sum.txt | while IFS= read -r FILE; do
  printf '%s\n' "${FILE}" | grep -Eq '^cert-[A-Za-z0-9.*-]+\.pem$' || exit 1
  curl --fail --http1.1 -sS \
    --output "${FILE}" "${BASE_URL}/${FILE}" || exit 1
done

sha256sum -c sha256sum.txt
```

The checksum command must report `OK` for `acme-account.json` and every
`cert-*.pem` entry. A persisted evidence directory can retain certificates from
previous domain configurations; review every manifest entry during an audit.

#### Step 3: Match the served certificate

```bash
echo | openssl s_client \
  -connect "${DOMAIN}:443" \
  -servername "${DOMAIN}" 2>/dev/null | \
  openssl x509 -fingerprint -sha256 -noout

openssl x509 -in "${CERT_FILE}" -fingerprint -sha256 -noout
```

The two SHA-256 fingerprints must match.

#### Step 4: Review issuance policy and history

```bash
# Certificate Transparency history
curl -s "https://crt.sh/?q=${DOMAIN}&output=json" | \
  jq -r '.[] | "\(.not_before) to \(.not_after): \(.issuer_name)"'

# ACME account used by the ingress
jq -r '.uri' acme-account.json

# Effective CAA response
dig +short CAA "${DOMAIN}"
```

Review every still-valid certificate and reconcile unexpected issuance. CAA
policy varies by DNS provider:

- Cloudflare and Linode can publish the account-bound policy requested by ingress
- Namecheap requires manual CAA management
- Route53 publishes a broader issuer policy at the hosted-zone apex
- `SET_CAA` defaults to `false` in direct DNS-01 mode
- Full DNS delegation requires CAA in the delegated zone

CAA constrains future issuance while the DNS policy remains intact. DNS
administrators can alter the record, and existing certificates remain valid
until expiration or revocation.

### Evidence Files Reference

| File | Contents |
|------|----------|
| `quote.json` | TDX quote returned by the guest agent |
| `sha256sum.txt` | SHA-256 manifest for the ACME metadata and `cert-*.pem` files |
| `cert-<domain>.pem` | Current certificate for one configured domain |
| `acme-account.json` | ACME directory, account URI, and optional public contact address |

`sha256sum.txt` excludes itself and `quote.json`. Its SHA-256 digest is placed in
the first half of the quote's 64-byte `report_data` field.

Evidence is regenerated after certificate issuance and actual renewal. Persist
both `/etc/letsencrypt` and `/evidences` so a restart preserves the certificate
state and its corresponding evidence.

### Troubleshooting

**Files missing at `/evidences/`**: Check that certificate issuance completed,
`EVIDENCE_SERVER=true`, the `/evidences` volume is mounted, and the logs contain
the evidence-generation step. `SET_CAA` does not control evidence generation.

**Certificate mismatch**: Renewal may have completed after the download.
Download the full evidence set again and repeat the manifest and quote checks.

**Quote verification failure**: Treat the evidence as untrusted. Check the guest
agent response, DCAP collateral, TCB status, and the TDX platform requirement.

**CAA mismatch**: Update or remove the active CAA RRset through the DNS provider.
Changing `SET_CAA` only controls future writes by dstack-ingress.

### Complete Trust Review

After the four checks above, verify the ingress compose hash, image digest, and
source against the application's attested measurements. This establishes which
code handled the certificate and private key. Continue with
[Application Attestation](/phala-cloud/attestation/overview).

## Next Steps

### Monitoring

Set up alerts on [crt.sh](https://crt.sh) to detect unexpected certificate issuance:
- Gateway domains: `%.dstack-pha-prod7.phala.network`
- Custom domains: `your-domain.com`

### Development

- **Gateway verification**: Integrate attestation checks into your security monitoring workflow
- **Custom domains**: Enable CAA records with `SET_CAA=true` in your deployment configuration
