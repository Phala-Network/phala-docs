---
title: Trust Boundary
description: Understand Phala's attested gateway, provider evidence coverage, and where plaintext exists.
---

Every model on `https://inference.phala.com/v1` uses the TEE-only serving policy. The Phala gateway requires upstream verification and channel binding before forwarding; if that fails, it refuses the request. The evidence covers different boundaries for different [providers](/phala-cloud/confidential-ai/confidential-model/providers).

## What the gateway protects

- **Gateway identity**: A fresh [attestation report](/phala-cloud/confidential-ai/confidential-model/api-reference/attestation) binds the gateway keyset to hardware evidence.
- **Per-response integrity**: A signed [receipt](/phala-cloud/confidential-ai/confidential-model/api-reference/receipts) binds request and response hashes to that keyset.
- **No body retention in receipts**: Receipts contain hashes and verification facts rather than prompt or response bodies.
- **Required upstream verification**: The gateway verifies the provider boundary and enforces channel binding before forwarding.
- **Optional retention constraint**: `provider: {"zdr": true}` restricts routing to serving routes that do not retain prompt or completion content. See [Zero Data Retention](/phala-cloud/confidential-ai/confidential-model/zero-data-retention).

## Limits

- **Plaintext is processed in the gateway TEE**: TLS terminates there. Field-level [E2EE](/phala-cloud/confidential-ai/confidential-model/e2ee-encryption) encrypts to an attested gateway key and decrypts inside that gateway.
- **Upstream coverage varies**: Some verifiers cover a model CVM, others a router or broker. Read the cited session's claims; gateway attestation does not independently attest every upstream model worker, GPU link, or model weight.
- **Client verification is explicit**: Ordinary clients do not verify the quote, pin TLS to the attested key, or audit receipts. Use the [TypeScript SDK](/phala-cloud/confidential-ai/verify/typescript-sdk) or [Private AI Proxy](/phala-cloud/confidential-ai/agents/private-ai-proxy).
- **Receipts are not a permanent public log**: Fetch them promptly and archive them if durable evidence is required.
- **Local tools remain separate**: Agent tools, MCP servers, browser automation, and telemetry can expose data outside the inference boundary.

## Where plaintext exists

| Stage | Plaintext boundary |
| --- | --- |
| Client to gateway | TLS protects transit; optional E2EE protects selected fields to the gateway's attested key. |
| Inside gateway TEE | The attested workload processes the request after TLS termination or E2EE decryption. |
| Gateway to provider | TLS pinned to a verified key or provider-specific E2EE binds the outgoing channel. |
| Inside provider | Depends on the verified model-instance, router, or broker boundary and the session's evidence. |

## Apply a policy

Verify the receipt and its session, then require the claims your workload needs. Add a compose allowlist from authenticated release metadata when you need reviewed gateway releases. Add zero data retention when post-request storage matters. Use a custom GPU TEE deployment when you need control over the complete serving workload.
